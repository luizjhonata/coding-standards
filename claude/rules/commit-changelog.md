# Commit Finalization and CHANGELOG Updates

When asked to finalize commits, update the changelog, or squash WIP commits, follow this workflow.

## Step 0: Detect Changelog Strategy

Check if `.chlog.yaml` exists in the project root:
- **Present** → use the **chlog workflow** (fragment-based). NEVER edit CHANGELOG.md directly.
- **Absent** → use the **legacy workflow** (direct CHANGELOG.md edit).

---

## chlog Workflow (fragment-based)

Applies to repos with `.chlog.yaml` (e.g., MSSP repos).

### Creating changelog entries

For each logical change in the PR, create a fragment:

```bash
chlog new -k <Kind> -b "<description>"
```

- **Kind**: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` (case-insensitive)
- **Body**: lowercase imperative description, wrap identifiers in backticks, append Jira link
- One fragment per logical change — multiple fragments per PR are fine

Example:

```bash
chlog new -k Added -b "health check endpoints \`/healthz\` and \`/readyz\` - [DS-5768](https://arancia.atlassian.net/browse/DS-5768)"
chlog new -k Added -b "environment-based config loading with sensible defaults - [DS-5768](https://arancia.atlassian.net/browse/DS-5768)"
```

### Staging fragments

The fragment file (`.changes/unreleased/<timestamp>-<hash>.yaml`) MUST be staged and committed alongside the code changes:

```bash
git add .changes/unreleased/
```

### CI gate

`chlog check` runs in CI and fails if no unreleased fragments exist. Every PR must include at least one fragment.

### Release workflow (maintainer only, not during regular PRs)

```bash
chlog batch auto        # compiles fragments into .changes/v<VERSION>.md, deletes fragments
chlog merge             # inserts version file into CHANGELOG.md, deletes version file
git add CHANGELOG.md .changes/
git commit -m "release: v<VERSION>"
git tag v<VERSION>
```

### Rules

- NEVER edit CHANGELOG.md directly — it is generated by `chlog merge`
- NEVER delete or modify fragment files manually — `chlog batch` consumes them
- Fragment body follows the same format as legacy CHANGELOG entries (lowercase verb, backticks, Jira link)

## Legacy Workflow (direct edit)

Applies to repos without `.chlog.yaml`.

### Step 1: Read and Analyze Commits

```bash
git log -N --format='%H%n%s%n%b%n---COMMIT_END---'
git log -N --stat
git diff HEAD~N..HEAD
git branch --show-current   # extract Jira ticket (e.g. feat/TICKET-1234 -> TICKET-1234)
```

### Step 2: Update CHANGELOG.md

Add entries under `## [Unreleased]`. Subsection order follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed`, `### Security`.

#### Entry Rules

- Lowercase past tense verb (`added`, `changed`, `fixed`, `removed`)
- Append Jira link: `- [TICKET-XXXX](https://company.atlassian.net/browse/TICKET-XXXX)`
- Wrap identifiers in backticks
- One entry per logical change
- Always append new entries **below** existing entries within the same subsection — never insert above them

#### Example

```markdown
### Added

- added 8 alert actions (`list_alerts`, `get_alert`, ...) to `CaseManagement` node - [TICKET-1234](https://company.atlassian.net/browse/TICKET-1234)

### Fixed

- fixed SMTP node to match TypeScript reference implementation - [TICKET-5678](https://company.atlassian.net/browse/TICKET-5678)
```

## Common Rules (both workflows)

### Squash WIP Commits

**NEVER squash without explicit user confirmation.** Show: number of commits, proposed message, wait for approval.

### Commit Message Format

```
type(TICKET-XXXX): concise imperative description

- imperative verb bullet points
- group related changes logically

Signed-off-by: <from git config>
```

Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
Title: max 72 chars, imperative mood, lowercase after colon, no trailing period.

### Signed-off-by Rule

NEVER hardcode the `Signed-off-by` trailer. Always use one of these approaches:
1. **Preferred**: `git commit -s` (or `--signoff`) — git populates the trailer from local config
2. **If amending with `-m`**: read `git config user.name` and `git config user.email` first, then use those values

Different repos have different identities configured (e.g., work email for Azure DevOps, personal email for GitHub). Hardcoding causes wrong signatures.

### Post-Squash

Remind user that `git push --force-with-lease` is required. NEVER force push without explicit request.
